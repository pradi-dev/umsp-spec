# System Overview

UMSP is not one monolithic protocol — it is a small set of subsystems that
share an identity model and a common event format, but are otherwise
allowed to use the transport and delivery model best suited to what they
do.

| Subsystem | Purpose | Transport | Delivery model |
|---|---|---|---|
| **Control plane** | DMs, channel messages, presence, typing, call signaling | HTTP + WebSocket | Real-time push |
| **Media repository** | Photos, videos, files, link-preview thumbnails, avatars | HTTP | Pull-on-first-request, then cached |
| **Voice/video** | Live audio/video in channels and calls | WebRTC (SRTP/DTLS over UDP), signaled via the control plane | Real-time streaming |
| **Feeds** | Profile timelines, following, explore/discovery | HTTP | Push (follow-feed, via shared-inbox fan-out) + pull (explore, via aggregators) |

This split exists because each of these has fundamentally different
requirements. See [Transport Layer](../protocol/transport.md) for the
normative detail, and [Federation Model](./federation.md) /
[Feeds & Discovery](./feeds.md) for why the delivery model differs between
channels and feeds.

## Servers vs. feeds: two different data models

A Discord/Slack-style **server** (a set of text/voice channels with a fixed
membership) and a Twitter/Instagram-style **feed** (a profile timeline with
followers) look similar on the surface but behave completely differently
under load, and so they are modeled differently in UMSP:

- A **channel** has a small, known set of participating homeservers. Every
  homeserver with a member in the channel keeps a full replica of its
  history (see [Federation Model](./federation.md)).
- A **feed** can have an unbounded number of followers spread across an
  unbounded number of servers, and additionally needs to support discovery
  by people who don't follow you yet. It is handled as a distinct
  subsystem (see [Feeds & Discovery](./feeds.md)) modeled after
  ActivityPub/Bluesky rather than the channel replication model.

## Rich messages

Every message (DM or channel) can carry structured attachments, not just
text — the LINE/WeChat-style "send a webpage" experience. A shared
webpage becomes a `link-preview` attachment carrying the URL plus
pre-fetched metadata (title, description, thumbnail), generated by the
sending client or its home server — never fetched blindly by the
receiving server, for both privacy and abuse-prevention reasons. See
[Messaging Events](../protocol/messaging.md).
